# Failure model and guarantees

PostgreSQL owns each execution, compiled action keys, approval, retry deadlines and leases. A semantic revision fences every domain update. A worker update also requires its current unexpired token on the actual SQL write, using PostgreSQL server time. Semantic state and audit commit together. Heartbeats and dispatch timestamps do not change the semantic revision. Saves update selected fields; they never replace stale snapshots.

Every due transition stores its deadline and advances its wake sequence atomically. The dispatcher commits enqueue intent before Redis publication. Publication loss recovers after five seconds. Redis messages are notifications, not action arguments. Workers reread PostgreSQL eligibility, so duplicate and stale messages are harmless. Redis deletion does not delete accepted work.

Before an HTTP mutation, the runner persists an IN_FLIGHT intent and increments the submission count. A crash after that point is ambiguous, even when the request may never have left the process. Recovery looks up the same persisted idempotency key. Only an adapter with durable same-key replay may resubmit after NOT_FOUND. NOT_FOUND does not exclude a late commit.

The local SQLite simulators atomically commit effects and indefinite idempotency ledgers. This controlled contract prevents duplicate effects across overlapping workers; a database lease alone cannot do that. Effect counts use a logical workflow/action ID independent of the idempotency key, so changing a key cannot hide a duplicate in benchmarks.

Unknown results, malformed success bodies and unclassified 5xx responses require reconciliation. Five submissions and five lookups per ambiguous episode are hard limits. Final unresolved ambiguity is NEEDS_REVIEW, including when a later known-no-effect rejection cannot exclude an earlier ambiguous submission. Key/payload conflict also stops for review.

Cancellation prevents remaining work only when no current lease or uncertain/in-flight action exists. An action waiting for same-key replay still has an unresolved earlier submission, even though its scheduling status is PENDING; cancellation rejects it until the outcome is confirmed. It never rolls back a ticket or stock reservation. A FAILED or CANCELLED workflow can retain a confirmed ticket. Stock shortage is a stored SKIPPED outcome and satisfies the conditional request.

Phase 1 denies new standalone admission/approval and all unauthenticated workflow reads/cancellation. General store admission/save cannot mint approval. Existing executor fixtures use a registered test-only owner capability and preserve exact plan hashes and stable action keys. They are not a production review mechanism. Schema readiness failure returns 503; Redis loss alone returns 200 degraded. No end-to-end exactly-once claim is made.

The historical MongoDB deployment/data remain separate and untouched. The PostgreSQL runtime change is not a data migration, replicated disaster-recovery design or finished review release. The new process/fault matrix and fresh Compose tests use isolated resources, not historical measurements or a running user's deployment.

The complete compact execution snapshot remains limited to 256 KiB. The private JSONB representation and its larger SQL rendering guard do not increase that budget. Exactly-full snapshots can lack operational metadata headroom; those individual writes roll back rather than committing an unreadable snapshot. Row-local due-marker failures cannot roll back healthy rows or permanently block a poisoned prefix. The scanner uses bounded, wrapping non-authoritative continuation; PostgreSQL remains the only durable due authority.

Deployment identity persists with its database, simulator ledgers and private credential volumes. Normal recreation/down-up retains all of them and does not reseed stock or allocate another database. Incomplete preparation and inconsistent recovery sets fail closed. An abrupt crash after fresh DDL but before the canonical credential record can still need explicit operator recovery. A durable started marker prevents an automatic second allocation; it is not a promise to reconstruct lost credentials or recover every filesystem/connection failure automatically.
